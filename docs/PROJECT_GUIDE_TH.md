# ไกด์วางแผนงานกลุ่ม: Bicycle Rental Demand Prediction

IFJC4002 | ฉบับเสนอเพื่อหารือในกลุ่ม | 27 ตุลาคม 2026

เอกสารนี้อธิบายแนวทางทำโครงงานทำนายความต้องการเช่าจักรยาน ตั้งแต่ทำความเข้าใจโจทย์จนส่งงานและสาธิต พร้อมทางเลือก ข้อดี และข้อจำกัด กลุ่มยังไม่ได้ตกลงเลือกโมเดลหรือรูปแบบระบบ ข้อเสนอทั้งหมดปรับได้หลังคุยกันและได้รับ dataset จากอาจารย์

ข้อมูลที่ยืนยันแล้ว: กลุ่มเลือก Bicycle rental demand prediction และอาจารย์จะจัดหา dataset ให้ จึงไม่ต้องหาหรือเลือก dataset เอง รายชื่อคอลัมน์ หน่วย ช่วงเวลา และคุณภาพข้อมูลยังต้องตรวจจากไฟล์จริง

## 1. หัวข้อนี้กำลังแก้ปัญหาอะไร

โจทย์คือใช้ข้อมูลที่เกี่ยวข้อง เช่น เวลา สภาพอากาศ และประเภทวัน เพื่อประมาณจำนวนครั้งที่มีการเช่าจักรยานในช่วงเวลาหนึ่ง งานนี้เป็น Regression หรือการทำนายค่าตัวเลข ตามกรณีที่ 3 ในโจทย์อาจารย์

ตัวอย่างเพื่อให้เห็นภาพ: ผู้ดูแลบริการเลือกช่วงเวลาที่ต้องการประเมิน กรอกข้อมูลตามที่ระบบรองรับ แล้วเห็นค่าประมาณ 120 ครั้งในหนึ่งชั่วโมง ตัวเลขนี้เป็นเพียงตัวอย่างอธิบายหน้าที่ของระบบ ยังไม่มีผลทดลองจริง

กลุ่มอาจกำหนดผู้ใช้เป็นผู้ดูแลบริการเช่าจักรยาน เพื่อใช้ข้อมูลประกอบการจัดเตรียมบริการในช่วงที่คนใช้งานมาก แต่ต้องดูว่า dataset มีข้อมูลรวมทั้งระบบหรือแยกแต่ละสถานี หากไม่มีรหัสสถานี ก็ยังอ้างว่าทำนายแยกสถานีไม่ได้

จำนวนครั้งที่เช่าไม่เท่ากับจำนวนจักรยานที่ต้องมีพร้อมกัน เพราะจักรยานหนึ่งคันอาจถูกเช่าหลายรอบ ผลทำนายจึงช่วยประเมินปริมาณการใช้งาน ส่วนการคำนวณจำนวนคันที่ควรเตรียมต้องมีข้อมูลและสมมติฐานเพิ่มเติม

ข้อดีของหัวข้อนี้: อธิบายปัญหาและผลลัพธ์ได้ตรงไปตรงมา ทำกราฟเปรียบเทียบตามเวลาได้ และเชื่อมการทดลองโมเดลกับหน้าจอใช้งานได้ชัด

ข้อจำกัด: พฤติกรรมการเช่าเปลี่ยนตามพื้นที่ ฤดูกาล และการเปิดบริการ ข้อมูลอดีตอาจไม่ครอบคลุมเหตุการณ์ใหม่ อีกทั้งยอดเช่าที่บันทึกได้อาจต่ำเพราะจักรยานไม่พอหรือระบบปิดบริการ จึงอาจสะท้อนความต้องการทั้งหมดไม่ได้

## 2. สิ่งที่อาจารย์กำหนด กับเรื่องที่กลุ่มเลือกได้

ข้อกำหนดจากโจทย์: ทำงานกลุ่ม 5 คน ใช้ข้อมูลตาราง วิเคราะห์ปัญหาและข้อมูล เปรียบเทียบอย่างน้อย 2 อัลกอริทึมที่เหมาะสม และมี baseline สำหรับเทียบ จากนั้นนำโมเดลที่กลุ่มเลือกไปใช้ใน Streamlit ทดสอบ และเผยแพร่ผ่าน GitHub กับ Streamlit Community Cloud

งาน Regression ต้องรายงาน MAE, RMSE และ R-squared ต้องเก็บโมเดลพร้อมขั้นตอนแปลงข้อมูลให้โหลดกลับมาใช้ได้ ตรวจว่าผลใน dashboard ตรงกับ notebook หรือสคริปต์ และมีหลักฐาน monitoring

งานส่งประกอบด้วยรายงาน PDF ประมาณ 8–12 หน้า ไม่รวมปก เอกสารอ้างอิง และภาคผนวก โค้ดที่รันได้ app.py, requirements.txt, โมเดลและ preprocessing, README, ข้อมูลหรือวิธีเข้าถึงข้อมูล ลิงก์ GitHub และแอป พร้อมหลักฐานการทดลอง การทดสอบ และผลงานสมาชิก

ต้องเก็บอย่างน้อย 5 prompts ที่เป็นตัวแทนของคนละช่วงพัฒนา พร้อมอธิบายว่าตรวจ แก้ หรือปรับโค้ดจาก AI อย่างไร สมาชิกทุกคนต้องเข้าใจงานและอธิบายส่วนที่ทำได้

เรื่องที่กลุ่มเลือกได้: ขอบเขตคำถาม รูปแบบหน้าจอ อัลกอริทึมที่จะทดลอง วิธีแบ่งงาน และความละเอียดของการวิเคราะห์ ภายใต้ข้อกำหนดและ dataset ที่อาจารย์ให้ ส่วนกำหนดส่งและตารางสาธิตต้องรอประกาศ ไม่ควรใช้ตารางเวลาในไกด์แทนกำหนดจริง

## 3. อ่านเกณฑ์คะแนนให้เห็นงานที่ต้องเตรียม

คะแนนรวม 80 คะแนน แบ่งเป็นรายงาน CO1 และ CO2 จำนวน 40 คะแนน โค้ด CO3 จำนวน 20 คะแนน และสาธิต CO3 จำนวน 20 คะแนน CO1 เน้นวิเคราะห์ปัญหาและข้อมูล CO2 เน้นออกแบบและประเมินโมเดล ส่วน CO3 เน้นทำระบบให้ทำงานจริงและอธิบายได้

รายงาน: ปัญหาและแนวทาง 5 คะแนน: ต้องระบุผู้ใช้ เป้าหมาย ข้อมูลเข้า และเหตุผลที่ใช้แนวทางนี้ เตรียมย่อหน้าปัญหาและแผนภาพข้อมูลเข้าไปสู่ผลทำนาย

รายงาน: วิเคราะห์ข้อมูลและประสิทธิภาพ 5 คะแนน: ต้องตีความกราฟและผลทดลองว่าเกี่ยวข้องกับการใช้งานอย่างไร เตรียมข้อสังเกตจากข้อมูลกับการวิเคราะห์กรณีที่โมเดลผิดมาก

รายงาน: ออกแบบวิธีแก้ 5 คะแนน: อธิบายลำดับทำงาน การเลือกคอลัมน์ การเตรียมข้อมูล การแบ่งชุดข้อมูล และการป้องกันข้อมูลรั่ว

รายงาน: พัฒนาโมเดล 10 คะแนน: ต้องมี 2 อัลกอริทึมและ baseline พร้อมค่า settings และเหตุผลที่ทดลอง บันทึกขั้นตอนให้ผู้อื่นทำซ้ำได้

รายงาน: ประเมินและเลือกโมเดล 10 คะแนน: เทียบด้วยชุดประเมินเดียวกัน ใช้ตัวชี้วัดถูกต้อง แยกข้อมูลทดสอบ วิเคราะห์ความผิดพลาด และมีเหตุผลรองรับการเลือกโมเดลสุดท้าย

รายงาน: ข้อจำกัดและการปรับปรุง 5 คะแนน: เชื่อมข้อจำกัดกับสิ่งที่พบจริง เช่น ผิดมากในช่วงยอดเช่าสูง แล้วเสนอการปรับปรุงที่ทำได้ พร้อมต้นทุนหรือข้อแลกเปลี่ยน

โค้ด: ทำซ้ำได้ 5 คะแนน: คนอื่นเปิดงานแล้วรันตั้งแต่ต้นได้ มีไฟล์ครบ เส้นทางไฟล์และไลบรารีถูกต้อง กำหนด seed ในส่วนที่มีการสุ่ม

โค้ด: เชื่อมโมเดลกับ dashboard 5 คะแนน: โหลดโมเดลและ preprocessing ถูกชุด ชื่อคอลัมน์ ชนิดข้อมูล และลำดับตรงกับตอนฝึก มีตัวอย่างผลที่ตรงกับ notebook

โค้ด: ตรวจข้อมูลเข้าและทดสอบ 5 คะแนน: มีกรณีทั่วไป ขอบเขต และค่าผิดรูปแบบ พร้อมพฤติกรรมที่คาดหวัง ผลจริง และวิธีจัดการข้อผิดพลาด

โค้ด: เผยแพร่และ monitoring 5 คะแนน: แอปเข้าถึงได้ มีไฟล์สำหรับ deploy มี logs หรือบันทึกที่ตรวจดูจริง และระบุสัญญาณที่ควรทบทวนโมเดล

สาธิต: ใช้งานแอป 5 คะแนน: แสดงการกรอกข้อมูลจนได้ผล อธิบายความหมาย และลองกรณีใหม่ที่ถูกต้อง

สาธิต: เข้าใจโค้ดและผลงาน 5 คะแนน: สมาชิกทุกคนอธิบายงานตนเองและเส้นทางการทำนายได้ รวมถึงวิธีตรวจโค้ดที่ AI ช่วยสร้าง

สาธิต: ทดสอบและแก้ปัญหา 5 คะแนน: ลองค่าขอบเขตหรือค่าผิด อธิบายว่าควรเกิดอะไร ชี้โค้ดที่รับผิดชอบ และไล่หาสาเหตุได้

สาธิต: deploy และ monitoring 5 คะแนน: เปิดแอปจริง แสดงบันทึก อธิบายเกณฑ์ทบทวน ข้อจำกัด และขั้นตอนอัปเดต

แต่ละหัวข้อมีระดับ Excellent = 4, Good = 3, Satisfactory = 2 และ Limited = 1 ถ้าไม่มีหลักฐานที่ประเมินได้ให้ 0 สูตรคือ (ระดับที่ได้ ÷ 4) × คะแนนเต็มของหัวข้อนั้น เช่น Good ในหัวข้อ 10 คะแนน เท่ากับ 7.5 คะแนน รวมคะแนนเต็ม 80 โดยไม่คูณ 80% ซ้ำ เกณฑ์ไม่ได้กำหนดว่าโมเดลต้องได้ R² เท่าใดจึงผ่าน

## 4. คำศัพท์พื้นฐานที่ใช้คุยงานร่วมกัน

Dataset คือชุดข้อมูล มักเป็นตารางที่แต่ละแถวแทนหนึ่งเหตุการณ์หรือหนึ่งช่วงเวลา ต้องยืนยันจากไฟล์ว่าแถวหนึ่งหมายถึงอะไร

Feature หรือ X คือข้อมูลที่ใช้ทำนาย เช่น อุณหภูมิหรือชั่วโมง Target หรือ y คือคำตอบที่ต้องการทำนาย เช่น จำนวนครั้งที่เช่า ห้ามเอาคำตอบปะปนอยู่ในข้อมูลเข้า

Model คือวิธีเรียนรู้ความสัมพันธ์จากตัวอย่าง Algorithm คือวิธีที่ใช้สร้างโมเดล เช่น Linear Regression หรือ Random Forest ส่วน hyperparameter คือค่าตั้งก่อนฝึก เช่น ความลึกของต้นไม้

Train คือข้อมูลที่ให้โมเดลเรียนรู้ Validation คือข้อมูลสำหรับเปรียบเทียบและปรับแนวทาง Test คือข้อมูลที่กันไว้ตรวจผลสุดท้าย หากใช้ test เลือกโมเดลซ้ำ ๆ ผลจะไม่น่าเชื่อถือเท่าเดิม

Baseline คือวิธีง่ายสำหรับเป็นจุดเทียบ เช่น ทายทุกแถวด้วยค่าเฉลี่ยของ target ในชุด train ต้องมี baseline เพิ่มจาก 2 อัลกอริทึม ไม่ควรนับ baseline เป็นโมเดลที่สอง

Preprocessing คือการเตรียมข้อมูล เช่น เติมค่าที่หาย แปลงหมวดหมู่ และปรับสเกล Pipeline คือการรวมขั้นตอนเหล่านี้กับโมเดล ให้ตอนฝึกและตอนใช้จริงทำเหมือนกัน

Overfitting คือโมเดลทำคะแนนดีกับข้อมูลฝึก แต่ทำได้แย่ลงเมื่อเจอข้อมูลใหม่ Data leakage คือมีข้อมูลที่ไม่ควรรู้ขณะทำนายหลุดเข้าไปในการฝึกหรือเลือกโมเดล จนคะแนนดูดีเกินจริง

Deployment คือการนำแอปขึ้นให้เปิดผ่านลิงก์ได้ Monitoring คือการติดตามพฤติกรรมแอป ข้อมูลเข้า และผลทำนาย เพื่อมองหาปัญหาหรือเหตุที่ต้องทบทวน

## 5. ทางเลือกเรื่องขอบเขตที่นำไปคุยกันได้

ทางเลือก A: ประมาณยอดเช่าภายใต้เงื่อนไขที่ผู้ใช้กำหนด เช่น เลือกเวลา อุณหภูมิ และประเภทวัน แล้วดูค่าประมาณ

ข้อดี: เห็นความสัมพันธ์ข้อมูลเข้ากับผลลัพธ์ได้ง่าย ไม่ต้องเชื่อม API อากาศ เหมาะกับการสาธิตการทำงานของโมเดล ข้อจำกัด: เป็นการประเมินตามสมมติฐานของผู้ใช้ จึงยังไม่ใช่บริการพยากรณ์ล่วงหน้าที่พิสูจน์ว่าใช้งานจริงได้

ทางเลือก B: ทำนายยอดเช่าล่วงหน้าในช่วงที่ระบุ เช่น ชั่วโมงถัดไปหรือวันถัดไป

ข้อดี: เชื่อมกับการวางแผนบริการได้ชัด ข้อจำกัด: ต้องกำหนดเวลาที่ออกคำทำนายและระยะล่วงหน้า ต้องมีข้อมูลที่ทราบ ณ เวลานั้นจริง เช่น พยากรณ์อากาศที่ออกไว้แล้ว การใช้สภาพอากาศจริงของอนาคตจะทำให้การประเมินไม่ตรงกับการใช้งาน

ทางเลือก C: ทำนายเฉพาะช่วงเปิดบริการ หรือรวมช่วงปิดบริการด้วย

ข้อดีของการจำกัดเฉพาะช่วงเปิด: ตีความการใช้งานได้ตรงบริบทขึ้น ข้อเสีย: ไม่ครอบคลุมทุกช่วงและต้องบันทึกการกรอง ส่วนการรวมทั้งหมดครอบคลุมข้อมูลมากกว่า แต่ศูนย์ที่เกิดจากการปิดบริการอาจถูกเข้าใจว่าไม่มีความต้องการ ต้องดูว่า dataset มีข้อมูลสถานะเปิดบริการหรือไม่

ระดับเวลา: หากข้อมูลรายชั่วโมง รายชั่วโมงช่วยเห็นช่วงเช้า–เย็น แต่มีความผันผวนและรายการมากขึ้น หากเป็นรายวัน ภาพรวมอาจอ่านง่ายกว่า แต่ไม่บอกช่วงเร่งด่วนและมีตัวอย่างน้อยลง ถ้าจะแปลงจากชั่วโมงเป็นวัน ต้องกำหนดวิธีรวมยอดและข้อมูลอากาศให้ถูกต้อง ถ้ามีเพียงข้อมูลรายวัน จะสร้างยอดรายชั่วโมงจริงขึ้นมาเองไม่ได้

ทุกทางเลือกต้องตั้งชื่อผลให้ตรงกับสิ่งที่ทดลอง และขออาจารย์ยืนยันขอบเขตก่อนพัฒนา

## 6. ทางเลือกเครื่องมือ โดยส่วนที่อาจารย์กำหนดยังคงเดิม

ฝึกโมเดลใน Google Colab: เปิด notebook ผ่านเว็บและแชร์กันดูได้สะดวก ข้อดีคือเริ่มเรียนรู้ได้โดยไม่ต้องตั้งเครื่องมาก ข้อจำกัดคือ runtime อาจหยุดและไฟล์ชั่วคราวหาย ต้องเก็บ notebook และผลลัพธ์ที่จำเป็นให้ครบ

ฝึกโมเดลด้วย Python ในเครื่อง: ใช้ notebook หรือสคริปต์ในโปรแกรมแก้โค้ด ข้อดีคือจัดโครงสร้างไฟล์และเชื่อมกับแอปในเครื่องได้สะดวก ข้อจำกัดคือต้องติดตั้ง Python และจัดการ environment ให้สมาชิกใช้ได้ใกล้เคียงกัน

อาจใช้ Colab ทดลองแล้วนำไฟล์โมเดลไปใช้กับแอป หรือทำทั้งหมดในเครื่องก็ได้ สิ่งที่ต้องส่งคือกระบวนการที่ทำซ้ำได้ ส่วน Streamlit, GitHub และ Streamlit Community Cloud เป็นข้อกำหนดของโจทย์ ไม่ใช่ตัวเลือกที่ต้องโหวตว่าจะตัดออกหรือไม่

เครื่องมือแต่ละตัวทำหน้าที่ต่างกัน: pandas อ่านและจัดตารางข้อมูล เครื่องมือวาดกราฟช่วยสำรวจข้อมูล scikit-learn ใช้เตรียมข้อมูล ฝึกและประเมินโมเดล Streamlit ทำหน้าจอ GitHub เก็บโค้ดและประวัติการเปลี่ยนแปลง ส่วน Google Docs ใช้ร่างรายงานและบันทึกงานร่วมกัน

## 7. แผนงานตั้งแต่เริ่มต้นจนจบ

### ช่วงที่ 1: อ่านโจทย์และเตรียมตัวระหว่างรอ dataset

ทำอะไร: อ่านโจทย์ร่วมกัน แยกข้อบังคับออกจากข้อเสนอ ทำรายการงานส่ง เปิดเอกสารกลาง และลองอ่านตารางตัวอย่างเพื่อเข้าใจแถว คอลัมน์ X และ y หากใช้ข้อมูลตัวอย่างเรียนรู้ ให้แยกจากข้อมูลและผลที่จะส่งจริง

ฝึกสั้น ๆ: เปิด CSV ดู 5 แถวแรก นับจำนวนแถวและคอลัมน์ ดูชนิดข้อมูล แล้วให้สมาชิกแต่ละคนอธิบายว่าหนึ่งแถวหมายถึงอะไร ยังไม่ต้องฝึกโมเดลโครงงานก่อนทราบข้อมูลจริง

ผลที่ควรมี: checklist งานส่ง สมุดคำศัพท์สั้น ๆ รายชื่อสมาชิกและรหัสนักศึกษา และรายการคำถามสำหรับอาจารย์

พร้อมไปต่อเมื่อ: ทุกคนอธิบายได้ว่ากำลังทำนายตัวเลขอะไร และรู้ว่าต้องส่งอะไรบ้าง

### ช่วงที่ 2: รับข้อมูลและตกลงความหมายของงาน

ทำอะไร: เก็บต้นฉบับ dataset แยกไว้ อ่านคำอธิบายจากอาจารย์ ตรวจว่าหนึ่งแถวเป็นชั่วโมง วัน หรือสถานี ระบุ target หน่วย พื้นที่ และช่วงวันที่ ถ้ามีหลายไฟล์ ตรวจว่าเป็นคนละช่วงเวลา คนละระดับการสรุป หรือชุด train/test ที่อาจารย์แยกไว้แล้ว

ทำพจนานุกรมข้อมูล: บันทึกชื่อคอลัมน์ ความหมาย หน่วย ชนิดข้อมูล ตัวอย่างค่า และทราบได้เมื่อใด คอลัมน์ที่ไม่เข้าใจให้ถามก่อนแปลงค่า รวมถึงขอแหล่งที่มาและเงื่อนไขการเผยแพร่ ไม่ควรสันนิษฐานว่าไฟล์ที่ได้รับอนุญาตให้นำขึ้น repository สาธารณะเสมอ

ผลที่ควรมี: สรุปขอบเขตหนึ่งหน้า พจนานุกรมข้อมูล และบันทึกข้อยืนยันจากอาจารย์ ระบุทางเลือกที่กลุ่มยังไม่ได้ตัดสินใจให้เห็นชัด

พร้อมไปต่อเมื่อ: ระบุ y ได้แน่นอน รู้ว่าแถวหนึ่งแทนอะไร และไม่มี feature ที่เป็นคำตอบหรือข้อมูลหลังเกิดเหตุปะปนอยู่

### ช่วงที่ 3: ตรวจคุณภาพและสำรวจข้อมูล

ทำอะไร: ตรวจจำนวนแถว ค่าหาย แถวซ้ำ ชนิดข้อมูล หน่วย ค่าติดลบ และวันเวลาที่ไม่ต่อเนื่อง แยกค่าผิดจริงออกจากค่าที่พบได้น้อย เช่น วันงานใหญ่ที่ยอดสูง ห้ามลบทิ้งเพียงเพราะตัวเลขสูง

สำหรับข้อมูลตามเวลา ให้กำหนดช่วง train/validation/test ก่อนวิเคราะห์เชิงตัดสินใจ แล้วใช้ train สำรวจรูปแบบและออกแบบวิธีเตรียมข้อมูล ตรวจโครงสร้างทั้งไฟล์ได้เท่าที่จำเป็น แต่ไม่ใช้ผลจาก test เลือก feature หรือวิธีปรับโมเดล

กราฟที่อาจทำตามคอลัมน์จริง: การกระจายยอดเช่า ยอดตามชั่วโมง วันทำงานเทียบวันหยุด ยอดตามเดือน และความสัมพันธ์กับอุณหภูมิหรือฝน แต่ละกราฟควรมีคำอธิบายว่าสังเกตอะไรและจะมีผลต่อการทดลองอย่างไร

ผลที่ควรมี: ตารางคุณภาพข้อมูล กราฟที่ตอบคำถามได้ และบันทึกข้อสงสัย เช่น ยอดศูนย์เป็นเพราะไม่เช่าหรือปิดบริการ

พร้อมไปต่อเมื่อ: อธิบายได้ว่าข้อมูลมีข้อจำกัดใด และจะจัดการค่าหาย ค่าผิด และแถวซ้ำอย่างไรพร้อมเหตุผล

### ช่วงที่ 4: วางวิธีแบ่งข้อมูลและป้องกันข้อมูลรั่ว

ทำอะไร: กำหนด train สำหรับเรียนรู้ validation สำหรับเลือกแนวทาง และ test สำหรับประเมินรอบสุดท้าย ใช้ชุดประเมินเดียวกันกับทุกโมเดลและ baseline บันทึกช่วงวันที่และจำนวนแถวของแต่ละชุดไว้

ทางเลือกหนึ่งคือแบ่งตามลำดับเวลา เช่น 60% แรกฝึก 20% ถัดมาตรวจเลือก และ 20% ท้ายทดสอบ ตัวเลขนี้เป็นเพียงตัวอย่าง ต้องดูช่วงฤดูกาลและจำนวนข้อมูลจริง ข้อดีคืออธิบายง่ายและจำลองการใช้ข้อมูลเก่าทำนายช่วงใหม่ ข้อเสียคือผลขึ้นกับช่วงที่กันไว้

อีกทางเลือกคือเก็บ test ท้ายสุด แล้วใช้การตรวจหลายรอบแบบเดินหน้าในส่วนข้อมูลก่อนหน้า เช่น TimeSeriesSplit ข้อดีคือดูความสม่ำเสมอได้หลายช่วง ข้อเสียคือใช้เวลาและต้องอธิบายวิธีพับข้อมูลเพิ่ม ตรวจช่วงเวลาที่ขาดและหน่วยข้อมูลก่อนใช้ค่าเริ่มต้นของเครื่องมือ [3]

ถ้างานอ้างว่าทำนายอนาคต ต้องรักษาลำดับเวลา การสุ่มแถวอาจทำให้ข้อมูลอดีตและอนาคตปะปนกัน ส่วนการสุ่มจะพิจารณาได้เมื่อคำถามเป็นการประมาณแถวอิสระและมีเหตุผลรองรับ พร้อมอธิบายว่าผลไม่ได้พิสูจน์ความแม่นสำหรับอนาคต

ถ้ามีหลายสถานีหรือหลายแถวต่อเวลา ให้กำหนดบทบาทของกลุ่มข้อมูลด้วย การทดสอบสถานีที่ไม่เคยเห็นต้องแยกสถานีระหว่างชุด แต่การทำนายช่วงอนาคตของสถานีเดิมอาจให้สถานีเดิมอยู่ทั้งสองชุดได้เมื่อรักษาลำดับเวลา ห้ามให้รายการเดียวกันหรือสำเนารายการข้ามชุด

การเติมค่าหาย การเรียนรู้หมวดหมู่ การปรับสเกล และการเลือก feature จากข้อมูล ต้อง fit จาก train เท่านั้น จากนั้น transform validation/test ด้วยขั้นตอนเดิม Pipeline ช่วยจัดลำดับงานและลดความผิดพลาด [2]

ผลที่ควรมี: แผนแบ่งข้อมูล กฎใช้ feature และแผนภาพ preprocessing → model → prediction

พร้อมไปต่อเมื่อ: ทุกคนอธิบายได้ว่าเหตุใด test จึงต้องแยกไว้ และข้อมูลเข้าแต่ละตัวทราบได้ขณะใช้งานจริงหรือไม่

### ช่วงที่ 5: ทำ baseline และทดลองโมเดล

ทำอะไร: สร้าง baseline จากค่าเฉลี่ย target ใน train แล้วทดลองอย่างน้อย 2 อัลกอริทึม ตั้งข้อมูลเข้าและชุดประเมินให้เทียบกันได้ การเตรียมข้อมูลแต่ละโมเดลต่างกันได้หากจำเป็นและอธิบายเหตุผล

เริ่มจาก settings ที่อธิบายได้ แล้วปรับทีละประเด็นบน validation หากเปลี่ยนทั้ง feature วิธีแบ่งข้อมูล และค่าตั้งพร้อมกัน จะบอกได้ยากว่าอะไรทำให้ผลต่าง

ผลที่ควรมี: บันทึกแต่ละการทดลอง ระบุวัน ผู้ทำ feature ค่าตั้ง ช่วงข้อมูล MAE/RMSE/R² เวลาโดยประมาณ และสิ่งที่พบ การทดลองที่ผลแย่ยังมีประโยชน์เมื่ออธิบายสาเหตุและสิ่งที่เรียนรู้ได้

พร้อมไปต่อเมื่อ: baseline และ 2 อัลกอริทึมรันได้ครบ และคนอื่นเปิดงานมาทำซ้ำตามคำแนะนำได้

### ช่วงที่ 6: เปรียบเทียบ วิเคราะห์ และเลือกภายหลังการทดลอง

ทำอะไร: เปรียบเทียบผล validation และข้อจำกัด วิเคราะห์ว่าผิดมากในช่วงเวลาไหนหรือยอดระดับไหน ถ้าผลดูดีผิดปกติ ให้ตรวจข้อมูลรั่วก่อนสรุป

ให้กลุ่มตกลงเหตุผลเลือกโมเดลจากความผิดพลาด ความเร็ว ขนาดไฟล์ และความเข้าใจในการอธิบาย หลังเลือกแนวทางและค่าตั้งแล้วจึงใช้ test ประเมินรอบสุดท้าย หากฝึกใหม่ด้วย train รวม validation ให้ทำเมื่อเลือกวิธีแล้ว และประเมิน artifact ตัวที่จะนำขึ้นแอปด้วย test ที่กันไว้

ผลที่ควรมี: ตารางผลเปรียบเทียบ แผนภาพค่าจริงเทียบค่าทำนาย ตัวอย่างที่ผิดมาก เหตุผลเลือกโมเดล และข้อจำกัดที่อ้างอิงผลจริง

พร้อมไปต่อเมื่อ: บอกได้ว่าโมเดลสุดท้ายดีกว่า baseline ตรงไหนหรือยังมีจุดด้อยใด โดยไม่อาศัยคะแนนตัวเดียว

### ช่วงที่ 7: สร้าง Streamlit และเชื่อมไฟล์โมเดล

ทำอะไร: บันทึก preprocessing กับโมเดลเป็น pipeline เดียว หรือแยกไฟล์แต่ควบคุมรุ่นให้ตรงกัน แล้วให้แอปโหลดกลับมาใช้ ไม่ฝึกโมเดลใหม่ทุกครั้งที่ผู้ใช้กดทำนาย

หน้าจอควรมีชื่อโครงงาน คำอธิบายสั้น ช่องกรอกที่ตรงกับ feature หน่วย ช่วงค่าที่รองรับ ปุ่มทำนาย และผลที่ระบุหน่วยเวลา เช่น ครั้งต่อชั่วโมง หากใช้ date เป็นตัวสร้างวันในสัปดาห์ ก็ไม่ควรให้ผู้ใช้เลือกวันในสัปดาห์ขัดกับวันที่นั้น

ทางเลือกหน้าจอแบบหน้าเดียว: กรอกและเห็นผลทันที ข้อดีคือใช้ง่ายและทดสอบน้อยกว่า ข้อเสียคือพื้นที่อธิบายผลจำกัด

ทางเลือกแบบแยกส่วน: ส่วนทำนาย ส่วนสำรวจข้อมูล และส่วนผลโมเดล ข้อดีคือใช้ประกอบการนำเสนอได้มากขึ้น ข้อเสียคือมีงานดูแลและทดสอบเพิ่ม เลือกได้ตามเวลาหลังระบบหลักทำงาน

กรณีโมเดลทายค่าติดลบ ต้องกำหนดว่าจะจัดการอย่างไร เช่น แสดงคำเตือน จำกัดค่าต่ำสุดเป็นศูนย์ หรือปรับแนวทางโมเดล หากตัดค่าหรือปัดเศษ ต้องบันทึกกฎและใช้กฎเดียวกันในการตรวจผลแอปกับผลทดลอง

ผลที่ควรมี: app.py ไฟล์โมเดล สัญญาข้อมูลเข้า และตัวอย่างผลที่ตรงกันระหว่าง notebook กับแอป โดยเทียบค่าดิบก่อนการจัดรูปแบบด้วยค่าคลาดเคลื่อนเล็กน้อยที่กำหนดไว้

พร้อมไปต่อเมื่อ: โหลดไฟล์ใน session ใหม่แล้วทำนายได้ โดยไม่ต้องพึ่งตัวแปรค้างใน notebook

### ช่วงที่ 8: ทดสอบและนำแอปขึ้นออนไลน์

ทำอะไร: ให้สมาชิกที่ไม่ได้เขียนส่วนนั้นลองรันจาก README ทดสอบกรณีทั่วไป ค่าขอบเขต และข้อมูลผิด แก้ปัญหาแล้วทดสอบกรณีที่เกี่ยวข้องซ้ำ จากนั้นนำไฟล์ขึ้น GitHub และ deploy บน Streamlit Community Cloud [4]

เตรียม requirements.txt ให้ตรงกับรุ่นที่ทดลอง ตรวจชื่อไฟล์และเส้นทางแบบสัมพันธ์กับโครงงาน เพื่อให้เครื่องออนไลน์ค้นไฟล์เจอ ตรวจสิทธิ์ข้อมูลก่อนอัปโหลด และไม่ใส่รหัสผ่านหรือกุญแจ API ใน repository

ผลที่ควรมี: ลิงก์ GitHub ลิงก์แอป ภาพหน้าจอ และ test log ที่มีผลจริง หลังแก้แล้วบันทึกสถานะใหม่ แต่อย่าลบหลักฐานปัญหาจนตรวจย้อนหลังไม่ได้

พร้อมไปต่อเมื่อ: เปิดจากเบราว์เซอร์อีกเครื่องหรือ session ใหม่ได้ ทำนายถูกขั้นตอน และผู้ประเมินเข้าถึงลิงก์ได้ตามสิทธิ์ที่จัดไว้

### ช่วงที่ 9: เก็บ monitoring และเขียนรายงาน

ทำอะไร: ทดลองใช้งานหลายสถานการณ์ ดู logs หรือบันทึก input/prediction ที่ไม่อ่อนไหว ระบุรุ่นโมเดล เวลา ผล และข้อผิดพลาด พร้อมอธิบายว่าข้อมูลแต่ละรายการบอกอะไรได้

ตัวอย่างสัญญาณทบทวนที่กลุ่มอาจกำหนด: มี input นอกช่วงข้อมูลฝึกซ้ำ ๆ แอปโหลดโมเดลไม่สำเร็จ หรือเมื่อมีคำตอบจริงแล้วพบ MAE สูงกว่าเกณฑ์ที่ตกลงต่อเนื่อง เกณฑ์ตัวเลขต้องตั้งจากบริบทและผลจริง ไม่ใช้เลขสมมติเป็นผลการติดตาม

ผลที่ควรมี: monitoring record ที่มีรายการจริง ข้อสังเกตอย่างน้อยหนึ่งเรื่อง และขั้นตอนเมื่อพบปัญหา เช่น ตรวจข้อมูลเข้า รวบรวมคำตอบจริง ฝึกใหม่ ประเมิน เปลี่ยนไฟล์โมเดล และทดสอบแอปซ้ำ

พร้อมไปต่อเมื่อ: รายงานทุกข้ออ้างสำคัญมีตาราง กราฟ บันทึก หรือไฟล์งานรองรับ และแยกผลที่ทำจริงออกจากแนวทางปรับปรุงในอนาคต

### ช่วงที่ 10: ตรวจชุดส่งและซ้อมสาธิต

ทำอะไร: ทดลองรันตั้งแต่ต้น เปิดลิงก์ทุกอัน ตรวจไฟล์กับ checklist ส่งออก Google Docs เป็น PDF แล้วตรวจจำนวนหน้า ตาราง ภาพ และอ้างอิง เตรียมแผนสาธิตและซ้อมให้ทุกคนพูดตามเวลาที่ได้รับ

ผลที่ควรมี: ชุดส่งที่เปิดได้จริง รายงาน PDF หลักฐานสมาชิกและ prompts และลำดับสาธิตที่ซ้อมแล้ว

พร้อมส่งเมื่อ: ทุกคนอธิบายเส้นทางตั้งแต่ข้อมูลเข้าไปจนผลทำนายได้ มีผู้ตรวจความครบถ้วนอีกคน และแก้ปัญหาที่พบในการซ้อมแล้ว

## 8. ทางเลือกโมเดลสำหรับนำไปหารือ

Linear Regression: เรียนรู้ความสัมพันธ์แบบเชิงเส้น ข้อดีคือฝึกเร็วและอธิบายแนวคิดง่าย ข้อจำกัดคือรูปแบบยอดเช่าตามเวลาและอากาศอาจซับซ้อนกว่านั้น อาจทายติดลบ ต้องเตรียมหมวดหมู่และออกแบบ feature ให้เหมาะสม [6]

Decision Tree Regressor: ใช้เงื่อนไขแตกแขนง ข้อดีคือแสดงตัวอย่างเส้นทางตัดสินใจได้และรับความสัมพันธ์ไม่เป็นเส้นตรง ข้อจำกัดคือต้นไม้ลึกอาจจำข้อมูลฝึกมากไป ต้องเปรียบเทียบความลึกและขนาดใบด้วย validation

Random Forest Regressor: รวมต้นไม้หลายต้น ข้อดีคือรองรับความสัมพันธ์ไม่เป็นเส้นตรงและลดความแปรปรวนของต้นไม้เดี่ยวได้ ข้อจำกัดคือไฟล์และเวลาฝึกอาจมากกว่า และอธิบายการทำนายรายตัวอย่างยากกว่าต้นไม้เล็ก [7]

ชุดเปรียบเทียบที่คุยกันได้: Linear Regression กับ Decision Tree ให้เห็นความต่างของแนวคิดและอธิบายได้ตรง ส่วน Linear Regression กับ Random Forest เปิดโอกาสทดสอบโมเดลที่ยืดหยุ่นขึ้น แต่มีภาระอธิบายและตรวจ settings มากขึ้น จะทดลองทั้งสามก็ได้หากเวลาพอ แต่ต้องยังทำหลักฐานและวิเคราะห์ให้ครบ

ทุกชุดต้องเพิ่ม baseline และยังไม่สรุปผู้ชนะก่อนทดลอง จำนวนโมเดลมากขึ้นไม่ได้ทำให้ได้คะแนนสูงขึ้นเอง

## 9. อ่าน MAE, RMSE และ R² อย่างไร

MAE คือค่าเฉลี่ยของความผิดพลาดแบบไม่สนเครื่องหมาย ค่ายิ่งต่ำยิ่งดี หน่วยเดียวกับ target เช่น MAE = 20 ครั้งต่อชั่วโมง หมายถึงคลาดเคลื่อนสัมบูรณ์เฉลี่ย 20 ครั้งต่อชั่วโมงในชุดที่ประเมิน ไม่ได้หมายความว่าทุกชั่วโมงผิดไม่เกิน 20

RMSE ให้น้ำหนักกรณีผิดมากเพิ่มขึ้น ค่ายิ่งต่ำยิ่งดีและหน่วยเดียวกับ target ถ้า RMSE สูงกว่า MAE มาก ให้ตรวจตัวอย่างที่ผิดหนัก เช่น ช่วงยอดเช่าพุ่ง

R² ใช้ดูความสามารถในการอธิบายความแปรปรวนเทียบกับการใช้ค่าเฉลี่ยของชุดที่ประเมิน ค่าสูงใกล้ 1 ดีกว่า ค่าติดลบเกิดได้และสะท้อนว่าผลแย่กว่าจุดอ้างอิงนี้ R² = 0.8 ไม่ควรแปลว่าแม่น 80% [5]

ตัวอย่างคำนวณสมมติ: ค่าจริง [100, 200] ค่าทำนาย [120, 160] จึงผิดสัมบูรณ์ [20, 40] MAE = (20 + 40) ÷ 2 = 30 และ RMSE = √((20² + 40²) ÷ 2) ≈ 31.62 ครั้ง ส่วน R² = 1 − 2,000 ÷ 5,000 = 0.60 ตัวอย่างสองรายการนี้ใช้สอนการอ่านค่า ไม่เพียงพอสำหรับสรุปประสิทธิภาพโครงงาน

ตารางผลจริงควรมีชื่อโมเดล ช่วงข้อมูลที่ประเมิน MAE RMSE R² ค่าตั้งหลัก และหมายเหตุ แยก validation ออกจาก test ให้ชัด ห้ามใส่ค่าตัวอย่างลงตารางแล้วปล่อยให้เข้าใจว่าเป็นผลทดลอง

## 10. จุดเสี่ยงเฉพาะหัวข้อจักรยาน

ผลรวมของคำตอบ: ถ้ามี casual และ registered ที่รวมกันเท่ากับยอดรวม target ต้องตัดทั้งคู่จาก X ไม่ควรให้โมเดลเห็นส่วนประกอบที่ทำให้คำนวณคำตอบตรง ๆ ได้ โจทย์อาจารย์เตือนเรื่องนี้ไว้แล้ว ชื่อเหล่านี้เป็นตัวอย่างจากชุดข้อมูลสาธารณะ ยังไม่ยืนยันว่าจะมีในไฟล์ของกลุ่ม

หน่วย: ตรวจว่าอุณหภูมิและความชื้นเป็นค่าจริงหรือค่าที่ถูกปรับสเกลมาแล้ว ถ้าหน้าจอรับ 30°C แต่โมเดลรอค่า 0–1 ต้องมีขั้นตอนแปลงที่ตรวจสอบได้

เวลา: วันที่ ชั่วโมง เดือน และวันในสัปดาห์เป็นข้อมูลเกี่ยวข้องกัน ต้องสร้างให้สอดคล้อง ตรวจรูปแบบวัน/เดือนและ timezone หากมีหลายพื้นที่

ค่าศูนย์: แยกความหมายว่าเป็นไม่มีการเช่า ปิดบริการ หรือข้อมูลหาย ไม่แทนค่าหายด้วยศูนย์โดยไม่มีเหตุผล

ยอดอดีต: การเพิ่มยอดชั่วโมงก่อนหน้าหรือค่าเฉลี่ยย้อนหลังเป็นทางเลือกต่อยอด แต่ต้องคำนวณจากอดีตเท่านั้นและมีข้อมูลนี้ขณะทำนายจริง ห้ามใช้ค่าเฉลี่ยที่รวมอนาคต หากเริ่มด้วย feature ทั่วไปจะมีภาระจัดการสถานะย้อนหลังน้อยกว่า

สภาพอากาศ: ถ้าเลือกพยากรณ์ล่วงหน้า ต้องไม่แอบใช้ค่าที่วัดหลังช่วงทำนายนั้น หากมีแค่อากาศจริงในอดีต ให้เขียนข้อจำกัดให้ตรงกับการทดลอง

การตีความ: ความสัมพันธ์ระหว่างฝนกับยอดเช่าไม่ได้พิสูจน์เหตุและผล ส่วน feature importance ไม่ได้บอกว่าปัจจัยนั้นเป็นสาเหตุโดยตรง

## 11. ตัวอย่างกรณีทดสอบและรูปแบบหลักฐาน

ทดสอบค่าทั่วไป: เลือกรายการที่อยู่ในช่วงข้อมูลฝึก คาดหวังให้ทำนายได้ แสดงหน่วยถูก และไม่มีข้อความผิดพลาด

ทดสอบค่าขอบเขต: หากเป็นข้อมูลรายชั่วโมง ลองชั่วโมง 0 และ 23 พร้อมค่าขอบเขตของ feature จริง คาดหวังให้ระบบรับค่าที่ถูกต้องโดยไม่ล่ม ขอบเขตทางกายภาพกับช่วงที่โมเดลเคยเห็นอาจต่างกัน จึงต้องกำหนดทั้งกฎห้ามและคำเตือน

ทดสอบค่าผิด: เช่น ความชื้น −1% หรือ 101% เมื่อหน่วยยืนยันว่าเป็นเปอร์เซ็นต์ คาดหวังให้ปฏิเสธและอธิบายการแก้ ไม่ส่งค่าผิดเข้าโมเดล หากหน้าจอป้องกันการกรอกอยู่แล้ว ให้ทดสอบ validation ในส่วนรับข้อมูลด้วย

ทดสอบ feature ไม่ครบหรือหมวดหมู่ไม่รู้จัก: คาดหวังให้จัดการตามกฎที่บันทึกไว้ เช่น แจ้งว่าข้อมูลใดขาดหรือรองรับหมวดหมู่ใหม่อย่างไร

ทดสอบ notebook เทียบ dashboard: ส่งข้อมูลดิบเดียวกันเข้าผ่าน pipeline เดียวกัน คาดหวังให้ผลตรงกันตาม tolerance ที่กำหนด ตรวจหน่วยก่อนและหลังแสดงผล

ทดสอบไฟล์โมเดลไม่พบหรือโหลดไม่ได้: จำลองในเครื่องพัฒนา คาดหวังให้แจ้งปัญหาที่อ่านรู้เรื่อง ไม่แสดงผลทำนายเก่าค้างเหมือนสำเร็จ

ทดสอบออนไลน์: เปิดแอปจาก session ใหม่และลองกรณีเดิม คาดหวังให้ได้ผลเดียวกับเวอร์ชันที่ตรวจในเครื่อง ตรวจสิทธิ์เข้าถึงและบันทึกรุ่นโมเดล

แบบบันทึก: Test ID | วันที่/ผู้ทดสอบ | รุ่นโค้ดและโมเดล | input | พฤติกรรมที่คาดหวัง | ผลจริง | ผ่าน/ไม่ผ่าน | หลักฐาน | วิธีแก้และผลตรวจซ้ำ การวางแผนกรณีทดสอบยังไม่ถือว่าได้ทดสอบแล้ว ต้องบันทึกผลหลังลงมือ

## 12. Monitoring แบบที่ทำได้ในงานกลุ่ม

ทางเลือกใช้ application logs: ดูข้อผิดพลาด การโหลดโมเดล และเหตุการณ์ใช้งาน ข้อดีคือเริ่มได้ง่ายและสอดคล้องกับโจทย์ ข้อจำกัดคืออาจค้นเปรียบเทียบเป็นตารางไม่สะดวก และไม่ควรเก็บข้อมูลอ่อนไหวลง log

ทางเลือกใช้บันทึกตารางหรือไฟล์ CSV ที่ดาวน์โหลดเก็บ: ระบุเวลา รุ่นโมเดล input สำคัญ prediction และหมายเหตุ ข้อดีคือแนบรายงานและตรวจย้อนหลังง่าย ข้อจำกัดคือต้องจัดการไฟล์และกำหนดวิธีเก็บรักษา หากพึ่งพื้นที่ชั่วคราวของแอปอย่างเดียวอาจไม่มีบันทึกต่อเนื่อง จึงควรเก็บสำเนาหลักฐานไว้

หากยังไม่มียอดเช่าจริงของคำทำนายใหม่ ให้รายงานได้ว่าแอปทำงานหรือ input เปลี่ยนไปอย่างไร แต่ยังสรุปความแม่นจริงจาก prediction อย่างเดียวไม่ได้ ถ้ามีคำตอบจริงภายหลัง จึงค่อยจับคู่ช่วงเวลาและคำนวณ error เพิ่ม

สิ่งที่แนบ: รายการที่เกิดจากการทดลองจริง ข้อสังเกตที่พบหนึ่งเรื่องขึ้นไป เกณฑ์เรียกทบทวน และผู้รับผิดชอบตรวจ ไม่สร้างเหตุการณ์ monitoring สมมติมาเขียนเป็นสิ่งที่เกิดขึ้นแล้ว

## 13. ทางเลือกแบ่งงานสำหรับสมาชิก 5 คน

แบบแบ่งตามส่วนงาน: คน A ดูปัญหาและข้อมูล คน B ดู preprocessing กับ split คน C ดู baseline และโมเดล คน D ดู dashboard กับ deploy คน E ดู testing, monitoring และประสานรายงาน ข้อดีคือเห็นเจ้าของงานชัด ข้อจำกัดคืองานหนักต่างกันและอาจมีคนเข้าใจเฉพาะส่วนตน

ถ้าใช้แบบนี้ ให้แต่ละคนเขียนรายงานในส่วนที่ทำและให้เพื่อนอีกคนตรวจ ผู้ประสานรายงานรวมรูปแบบและตรวจความต่อเนื่อง ไม่ควรต้องเขียนทุกส่วนแทนคนอื่น ทุกคนควรได้ทดลองโค้ดหรือทดสอบพร้อมหลักฐานจริง

แบบจับคู่และสลับผู้ตรวจ: แบ่งงานข้อมูล โมเดล และแอปเป็นงานย่อย มีเจ้าของและผู้ตรวจต่างคนกัน แล้วหมุนเวียนให้ครบ ข้อดีคือส่งต่อความรู้และลดการพึ่งคนเดียว ข้อจำกัดคือต้องนัดเวลาและควบคุมเวอร์ชันไฟล์

แบบทำตามช่วงร่วมกัน: ทุกคนผ่านข้อมูลและโมเดลรอบแรกด้วยกัน ก่อนแยกไปทำงานย่อย ข้อดีคือพื้นฐานร่วมกันแน่นขึ้น ข้อจำกัดคือเวลานัดกลุ่มมากและงานขนานช่วงแรกน้อย

บันทึกผลงานแต่ละคนเป็น ชื่อ/รหัสนักศึกษา → งานเฉพาะ → ไฟล์หรือผลลัพธ์ → หลักฐาน → ผู้ตรวจ → วันที่ ตัวอย่างหลักฐานคือ commit, notebook section, test log หรือภาพจากการทดลอง ใช้สิ่งที่ทำจริงและตรวจย้อนกลับได้

## 14. ตารางเวลาตัวอย่างที่ปรับได้

ช่วงรอข้อมูล: อ่านโจทย์ ฝึกอ่าน CSV เรียนรู้คำศัพท์ เตรียม checklist และคำถาม ไม่ผูกกับจำนวนวันเพราะยังไม่ทราบวันรับข้อมูล

ตัวอย่างเมื่อมีเวลาหลังรับข้อมูลประมาณ 4 สัปดาห์: สัปดาห์แรกยืนยันขอบเขต ตรวจข้อมูล และวาง split สัปดาห์ที่สองทำ preprocessing, baseline และเปรียบเทียบโมเดล สัปดาห์ที่สามเชื่อม Streamlit ทดสอบและ deploy สัปดาห์สุดท้ายเก็บ monitoring ปิดรายงาน ตรวจชุดส่ง และซ้อม

ข้อดีของกรอบนี้คือมีเวลาส่งต่อและแก้ปัญหา ข้อจำกัดคือใช้ไม่ได้ตรง ๆ หากข้อมูลมาช้าหรือกำหนดจริงสั้นกว่า ควรเขียนรายงานและเก็บหลักฐานระหว่างทำทุกช่วง เพื่อไม่ให้ภาระไปรวมท้ายงาน

หากเวลาน้อย ให้ลดฟีเจอร์เสริม เช่น หน้าแสดงข้อมูลหลายหน้า API อากาศ หรือโมเดลที่สาม แต่ยังต้องเก็บข้อบังคับ ได้แก่ 2 อัลกอริทึมพร้อม baseline ตัวชี้วัดครบ แอปออนไลน์ การทดสอบ monitoring และหลักฐานสมาชิกกับ prompts

จุดตรวจของกลุ่ม: หลังอ่านข้อมูลให้ยืนยันความหมาย หลังทดลองให้ทบทวนวิธีประเมิน ก่อนต่อแอปให้ตกลงสัญญา input/output และก่อนส่งให้คนอื่นรันตาม README หากช่วงใดยังไม่ผ่าน ให้แก้ข้อที่เป็นเหตุส่งต่อไม่ได้ก่อนเพิ่มฟีเจอร์

## 15. โครงสร้างไฟล์ที่อาจใช้

README.md: อธิบายโจทย์ แหล่งข้อมูล วิธีติดตั้ง ฝึก โหลดโมเดล รันแอป และ deploy พร้อมลิงก์ที่ตรวจแล้ว

notebooks/training.ipynb หรือ train.py: เลือกตามวิธีทำงาน บรรจุการอ่านข้อมูล split, preprocessing, baseline, โมเดล และการประเมิน หากใช้สองอย่างพร้อมกันต้องระบุว่าตัวไหนเป็นขั้นตอนหลัก

app.py: หน้าจอ Streamlit การตรวจ input การโหลด pipeline และการแสดงผล

requirements.txt: รายชื่อไลบรารีและรุ่นที่ใช้ทดสอบให้ environment สอดคล้องกัน

models/final_pipeline.joblib: ตัวอย่างชื่อไฟล์โมเดลรวม preprocessing หากใช้รูปแบบอื่นให้ระบุวิธีโหลดและความสัมพันธ์ของไฟล์

data/README.md: ความหมายข้อมูล แหล่งที่มา สิทธิ์เผยแพร่ และวิธีดาวน์โหลดหรือขอไฟล์ เก็บข้อมูลต้นฉบับในที่อนุญาต และป้องกันการอัปโหลดโดยเผลอหากห้ามเผยแพร่

results/: ตารางผล กราฟ และ metadata ของแต่ละการทดลอง

evidence/: test log, monitoring record, ภาพ dashboard, prompt record และ contribution record

report/: รายงานฉบับแก้ไขและ PDF ส่งจริง ชื่อและโครงสร้างนี้เป็นข้อเสนอ กลุ่มเปลี่ยนได้ตราบที่หาไฟล์และทำซ้ำได้

## 16. โครงรายงานและหลักฐานที่ควรเก็บระหว่างทำ

โครงตามอาจารย์: 1) ปัญหาและวิเคราะห์ข้อมูล 2) ออกแบบและ preprocessing 3) พัฒนาและเปรียบเทียบโมเดล 4) เลือกโมเดล ข้อจำกัด และการปรับปรุง 5) ระบบ dashboard, deploy, testing และ monitoring 6) บทสรุปและอ้างอิง ส่วน contribution, prompts และหลักฐานทดสอบเพิ่มเติมใส่ภาคผนวก

การจัดพื้นที่ 8–12 หน้าอาจเริ่มจากปัญหาและข้อมูล 2 หน้า ออกแบบ 1–2 หน้า โมเดลและผลเปรียบเทียบ 2–3 หน้า เหตุผลเลือกและข้อจำกัด 1 หน้า ระบบและหลักฐาน 2–3 หน้า แล้วปรับรวมให้เข้าเงื่อนไขจริง ตรวจหลังส่งออก PDF เสมอ ปก อ้างอิง และภาคผนวกไม่นับในช่วงหน้าที่กำหนด

เก็บหลักฐานตอนเกิดงาน: หลังสำรวจให้เก็บกราฟและคำอธิบาย หลังฝึกให้เก็บ settings และผล หลังแก้บั๊กให้เก็บ test log หลัง deploy ให้เก็บลิงก์กับภาพ และหลังใช้ AI ให้เก็บ prompt กับวิธีตรวจทันที

prompt record ควรครอบคลุมอย่างน้อย 5 ช่วง เช่น เข้าใจข้อมูล ออกแบบ preprocessing ทดลองโมเดล สร้างแอป และตรวจบั๊ก แต่ละรายการบันทึกคำถามจริง สิ่งที่นำมาใช้ สิ่งที่แก้ และหลักฐานที่ทำให้เชื่อว่าโค้ดถูกต้อง เช่น เทียบสูตร อ่านเอกสาร ทดลอง input หรือเทียบผล ห้ามใช้คำว่า “ตรวจแล้ว” โดยไม่บอกวิธี

## 17. แผนสาธิตตัวอย่างสำหรับหารือ

โจทย์เสนอเวลาสาธิตกลุ่ม 10 นาที และถามตอบ 5 นาที ต้องให้สมาชิกทั้ง 5 คนมีส่วนร่วม เวลานี้ยังต้องยึดประกาศอาจารย์อีกครั้ง

ตัวอย่างแบ่ง 10 นาที: คนที่ 1 ใช้ 1.5 นาทีอธิบายปัญหาและข้อมูล คนที่ 2 ใช้ 2 นาทีอธิบาย split/preprocessing และข้อมูลรั่ว คนที่ 3 ใช้ 2 นาทีอธิบาย baseline ผลเทียบ และเหตุผลเลือก คนที่ 4 ใช้ 2.5 นาทีเปิดแอปทำนายกรณีใหม่และลองค่าผิดหรือขอบเขต คนที่ 5 ใช้ 2 นาทีแสดงหลักฐาน testing/monitoring และขั้นตอนอัปเดต

ข้อดีคือผูกแต่ละช่วงกับเกณฑ์ได้ ข้อจำกัดคือเวลาเปิดลิงก์หรือโหลดไฟล์อาจกินเวลา จึงควรซ้อมจริงและย่นคำอธิบายที่ซ้ำ เตรียมภาพหรือวิดีโอสำรองประกอบ แต่ต้องมีแอปใช้งานจริงตามโจทย์

คำถามที่ทุกคนควรตอบได้: y คืออะไรและหน่วยอะไร X มีอะไร ทำไมเลือกคอลัมน์เหล่านี้ แบ่งข้อมูลอย่างไร baseline คืออะไร อ่าน MAE/RMSE/R² อย่างไร ทำไมเลือกโมเดลนี้ กรณีใดผิดมาก แอปใช้ preprocessing เดิมได้อย่างไร และจะรู้ได้อย่างไรว่าโมเดลควรถูกทบทวน

## 18. วาระคุยกลุ่มรอบแรกและคำถามสำหรับอาจารย์

รอบแรกอาจใช้ 30–45 นาที: ทวนข้อบังคับ 10 นาที คุยขอบเขตที่สนใจ 10 นาที เลือกวิธีร่วมงานกับเจ้าของงานเตรียมตัว 10 นาที แล้วบันทึกเรื่องที่รอ dataset หรือรอคำตอบอาจารย์ เวลานี้เป็นข้อเสนอเพื่อจัดประชุม

รายการคุย: อยากให้ระบบตอบคำถามใด ผู้ใช้คือใคร สนใจการประเมินตามเงื่อนไขหรือพยากรณ์ล่วงหน้า ใครสะดวกใช้ Colab หรือเครื่องตนเอง จะจับคู่ตรวจงานอย่างไร นัดทบทวนเมื่อใด และมีเวลาเหลือหลังได้รับข้อมูลเท่าใด

คำถามอาจารย์: dataset ให้เมื่อใด หนึ่งแถวและ target หมายถึงอะไร มี data dictionary หรือไม่ แหล่งข้อมูลและสิทธิ์เผยแพร่เป็นอย่างไร มี train/test ที่ต้องใช้ตามกำหนดหรือไม่ ต้องการพยากรณ์ล่วงหน้าหรือประเมินตามเงื่อนไขได้ ภาษาในรายงานและสาธิตกำหนดอย่างไร และกำหนดส่งกับสาธิตวันใด

รูปแบบบันทึกการตัดสินใจ: ประเด็น → ตัวเลือก → ข้อดี/ข้อจำกัด → มติของกลุ่มหรือรอข้อมูล → เหตุผล → ผู้รับผิดชอบติดตาม → วันทบทวน ไม่จำเป็นต้องตัดสินใจทุกอย่างในการคุยครั้งแรก

## 19. Checklist ก่อนส่ง

- ขอบเขตและข้อมูลได้รับการยืนยันกับอาจารย์แล้ว อธิบาย target หน่วย และเวลาที่ทำนายได้ตรงกัน
- วิเคราะห์คุณภาพข้อมูลและมีเหตุผลรองรับการใช้ feature/preprocessing พร้อมป้องกันข้อมูลรั่ว
- มี baseline เพิ่มจากอย่างน้อย 2 อัลกอริทึม เทียบด้วยชุดเดียวกัน และบันทึก settings
- มี MAE, RMSE และ R² พร้อมวิเคราะห์ข้อผิดพลาด เหตุผลเลือกโมเดล และข้อจำกัด
- notebook หรือสคริปต์รันตั้งแต่ต้นได้ โหลดโมเดลกับ preprocessing ใหม่ได้ และแอปให้ผลตรงกัน
- แอปตรวจ input ผ่านกรณีทั่วไป ขอบเขต และค่าผิด มี test log พร้อมผลจริงและการตรวจซ้ำ
- ลิงก์ GitHub กับ Streamlit ใช้งานได้ ไฟล์ครบ README ทำตามได้ และจัดสิทธิ์ข้อมูลถูกต้อง
- มี monitoring record ที่ตรวจจริง พร้อมสัญญาณทบทวนและขั้นตอนดูแล
- รายงาน PDF อยู่ในช่วงหน้าที่กำหนด ภาพและตารางอ่านได้ มีอ้างอิงและภาคผนวกครบ
- มีรายชื่อและรหัสสมาชิกทั้ง 5 คน งานเฉพาะพร้อมหลักฐาน และอย่างน้อย 5 prompts พร้อมวิธีตรวจหรือแก้
- ทุกคนได้ซ้อมและร่วมสาธิต อธิบายโค้ดและเส้นทางการทำนายได้
